# Автоматические проверки, сборка и обновление VPS

Workflow: `.github/workflows/ci-cd.yml`. Рабочая ветка — `main`, каталог сервера — `/srv/el-bebe`.

## Что запускается

- Pull request в `main`: `npm ci`, все тесты, Astro check, серверная и статическая сборки, проверка Compose и Bash. Доступ к VPS отсутствует.
- Push в `main`: те же проверки, сборка Linux Docker-образа и, после подключения сервера, обновление VPS.
- Публикация или снятие публикации в EmDash: тот же workflow через GitHub API. Обычное сохранение черновика его не запускает. Удаление записи публичной коллекции тоже запускает обновление; EmDash в событии удаления не передаёт прежний статус.
- Ручной запуск: GitHub → Actions → Site checks and VPS deployment → Run workflow, ветка `main`.

Серверный сайт читает опубликованный контент из CMS при запросе; HTML отдаётся с `Cache-Control: no-store`. Правка видна сразу, независимо от завершения пересборки. Новый образ содержит код и публичные файлы из Git, а существующая база и загрузки подключаются на VPS. Локальный статический Vercel showcase не получает CMS-базу и не является боевым сайтом.

Плагин ставит в приватной `office.sqlite` только номер изменения и служебное время. Пауза после последней публикации — 30 секунд, проверка очереди — каждые 30 секунд. Серия правок объединяется. При сетевой ошибке, 403 или истёкшем токене запись остаётся, повтор — через 1, 2, 4 минуты и далее, максимум раз в час. После перезапуска очередь сохраняется. Отправляются только причина `cms` и номер изменения; имён, телефонов, заявок и текста CMS в GitHub нет. Приватные документы и настройки получателя заявок сборку не запускают.

Принятие запроса GitHub снимает запись с очереди; оно **не означает успешный деплой**. Ошибка тестов или обновления видна в Actions, её исправляют и повторяют Run workflow. При неопределённом результате сетевого запроса возможен повторный запуск; workflow выполняется последовательно. Для одного экземпляра приложения, как в текущем Compose.

## Первое подключение

1. На VPS с Docker Engine + Compose импортировать существующую CMS, загрузки и ключ по `docs/DOCKER-VPS.md`. Проверить штатный вход и HTTPS. Автодеплой намеренно откажется запускать пустой сайт. Миграцию кабинета директора выполнить до переноса по `docs/CMS-DIRECTOR.md`.
2. Рабочий каталог `/srv/el-bebe` должен принадлежать отдельному пользователю деплоя. Ему нужны Bash, `flock` (util-linux), curl, sha256sum, SSH и доступ к Docker. Доступ к Docker даёт управление сервером — SSH-ключ предназначен только этому репозиторию. Секреты и каталоги releases/backups закрыть от других пользователей.
3. Настроить переменные GitHub и SSH-секреты ниже. Сначала оставить `DEPLOY_ENABLED=false`, дождаться успешной сборки образа. Значение по умолчанию без переменной — деплой выключен.
4. Создать отдельный fine-grained GitHub token: только репозиторий `JakuninOleg/ElBebe`, разрешение **Actions: Read and write**. Не нужны права изменения исходников. Сохранить токен на VPS в `deploy/secrets/github-actions-token`, владелец uid/gid `1000:1000`, права `0400`. Например, сначала безопасно передать файл вне сайта, затем:

   ```bash
   sudo install -m 0400 -o 1000 -g 1000 /private/github-actions-token \
     /srv/el-bebe/deploy/secrets/github-actions-token
   ```

5. В `deploy/.env` указать `CMS_REBUILD_REPOSITORY=JakuninOleg/ElBebe`. Токен не помещать в `.env`, Git, образ или GitHub artifact. Базовый Compose продолжает работать без токена; для очереди используется дополнительный `compose.cicd.yaml`, подключаемый новым деплоем.
6. Установить `DEPLOY_ENABLED=true`, запустить workflow вручную на `main`. Он добавит CMS worker вместе с новым образом. После успешного запуска опубликовать одну согласованную правку и убедиться, что появился запуск с причиной `cms`. Не использовать dev-bypass на VPS.

Ниже перечислены имена настроек, значения секретов в переписку не отправлять.

**GitHub → Settings → Secrets and variables → Actions → Variables:**

- `SITE_URL` — полный боевой origin, например `https://садик.ru` в ASCII/punycode форме, без завершающего `/`. Должен совпадать с `https://${DOMAIN}` из `deploy/.env`.
- `DEPLOY_ENABLED` — `true` только после готовности VPS, DNS, HTTPS, импорта и секретов.

**GitHub → Settings → Secrets and variables → Actions → Secrets:**

- `VPS_HOST` — IPv4 или ASCII hostname сервера.
- `VPS_SSH_USER` — отдельный пользователь деплоя.
- `VPS_SSH_PORT` — необязательно, по умолчанию `22`.
- `VPS_SSH_KEY` — приватный SSH-ключ этого пользователя; соответствующий публичный ключ установлен на VPS.
- `VPS_SSH_KNOWN_HOSTS` — проверенная запись ключа сервера в формате OpenSSH known_hosts. Отпечаток сверяется через доверенную консоль Beget. При нестандартном порте запись имеет вид `[host]:port ...`. Workflow использует `StrictHostKeyChecking=yes` и не принимает новый ключ сервера автоматически.

Environment `production` используется только job деплоя. Дополнительные правила подтверждения в нём задаёт владелец репозитория, если они нужны. Текущая схема не добавляет обязательное ручное подтверждение.

У токена на локальном компьютере сейчас нет доступа к API Actions variables/secrets (GitHub возвращает 403). Эти значения нужно внести учётной записью владельца или дать инструменту соответствующий доступ. Без сервера и этих настроек workflow сможет проверить код и собрать образ, но не сможет обновить VPS.

## Как обновляется сервер

GitHub собирает образ по точному commit SHA и lock-файлу, добавляет уникальный tag с номером запуска, передаёт сжатый образ и Compose/Caddy-конфигурацию по SSH. Серверу не нужен токен реестра контейнеров; новый образ загружается через `docker load`. Загрузка баз, CMS-ключа и пользовательской медиатеки в GitHub не производится.

Перед отправкой проверяется, что SHA ещё соответствует `main`. На сервере есть отдельная блокировка `flock` и проверка номера запуска: старый релиз не заменит уже установленный новый. Активный деплой не отменяется следующим push. GitHub может объединять ожидающие запуски; последний образ использует текущую CMS-базу.

`deploy/apply-release.sh` проверяет контрольные суммы, конфигурацию и существующий контейнер, сохраняет предыдущий образ и файлы конфигурации. Затем:

1. Кратковременно останавливает приложение, чтобы прекратить запись.
2. Создаёт консистентные SQLite snapshots CMS и office в `deploy/backups/<run-id>-<attempt>`. Не копирует десятки мегабайт неизменяемых медиа при каждой публикации.
3. Поднимает новый образ с `docker compose up --wait`, проверяет встроенный healthcheck с реальным запросом к CMS и соответствие запущенного образа.
4. Перезагружает Caddy и проверяет публичный HTTPS-адрес. Сохраняет текущий tag в `deploy/releases/current-image`.

При ошибке после остановки возвращаются прежние конфигурация и образ. Workflow остаётся красным, даже если возврат успешен. Резервные копии баз и постоянный том сохраняются. Базы автоматически назад не откатываются, чтобы не удалить свежие заявки. Для несовместимой миграции будущей версии CMS требуется ручное восстановление в новый том по DOCKER-VPS.md. Перед обновлением самой EmDash сначала проверять миграцию на копии.

Краткий перерыв на снимки и перезапуск предусмотрен; это не схема без простоя. Успешно загруженный tar-архив удаляется, образ остаётся в Docker. Старые образы и snapshots автоматически не удаляются: включите мониторинг диска, храните нужные последние версии и делайте полные бэкапы базы + медиа + ключа вне VPS. Не используйте `docker volume prune` и `compose down -v` для очистки.

Для остановки автодеплоя установить `DEPLOY_ENABLED=false`. Чтобы прекратить также запуски от CMS, убрать override из рабочего Compose и пересоздать приложение базовым Compose или отозвать токен. При отзыве очередь продолжит безопасные повторы, без потери опубликованных данных. После автодеплоя ручные команды Compose должны включать `-f compose.yaml -f compose.cicd.yaml` и текущий `IMAGE_TAG` из `deploy/releases/current-image`; иначе `.env` может выбрать старый ручной tag.

## Проверки

`npm run build:showcase`, затем `npm test`: проверки навигации и видео читают собранный HTML. Тесты включают реальные SQLite WAL snapshots, дебаунс/перезапуск/повтор очереди и конкурентную публикацию во время отправки. Bash-сценарии с подменённым Docker проверяют успех, повреждённый пакет, устаревший запуск, сбой snapshot, healthcheck, внешнего HTTPS и возврата образа; данные остаются на месте. Они не заменяют запуск Docker-контейнеров.

Локально проверены обе сборки, типы, Compose с объединёнными secrets и workflow через actionlint. Docker Engine на текущем Windows-компьютере отсутствует; Linux-образ впервые реально соберётся в GitHub Actions. Первый запуск с перенесённой CMS и реальный rollback должны быть проверены на VPS перед запуском сайта. Закрытие индексации сохраняется.

Официальные источники: [запуск workflow через API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event), [триггеры GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), [Compose up и ожидание healthcheck](https://docs.docker.com/reference/cli/docker/compose/up/).
